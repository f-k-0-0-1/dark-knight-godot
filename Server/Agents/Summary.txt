1. SYSTEM ARCHITECTURE OVERVIEW
-------------------------------------------------------------------
The networking pipeline has been completely refactored to run as a native GDScript implementation, replacing the compiled C socket binaries (peer.c and server.c) [1]. This architecture eliminates external compilation dependencies, platform execution warnings, and socket handshake drops [1].

- SERVER (TCPServer): A native background listener that binds to your local port, accepts incoming TCP connections, upgrades them to WebSocket connections, and processes incoming data frames natively on the main thread [1].
- CLIENT (WebSocketPeer): A native persistent WebSocket client that establishes a continuous, secure connection to the host address [1]. Sockets are kept alive throughout the game session, ensuring instantaneous delivery without socket handshake latency [1].

-------------------------------------------------------------------
2. RECENT STABILIZATION & REFACTORING UPDATE
-------------------------------------------------------------------

A. Pure GDScript WebSocket Migration
- Removed all compiled C binaries, UNIX parent-child thread warnings, and taskkill requirements [1].
- Integrated persistent, bi-directional client/server connections to avoid socket-handshake latency and eliminate packet drops [1].

B. Dynamic Port Probing & Auto-Detection
- Retired the lock-file (`testing_pid.lock`) and subprocess PID-checking system (`isPidActive()`) [1].
- Implemented a self-healing port-probing check: the application attempts to bind to port 8080 on startup [1]. If successful, it configures as Player 1 (Port 8080) [1]. If port 8080 is blocked, it binds to 8081 and configures as Player 2 (Port 8081) [1].

C. Reverse-Lookup Cloudflare Log Parser
- Overhauled the log-parsing logic inside `sync_node.gd` [1]. The parser finds `.trycloudflare.com` first, then searches backwards (`rfind`) to isolate the preceding `"https://"` [1]. This prevents website terms-of-service links from polluting your clipboard [1].
- Expanded the tunnel-timer handshake window from 5 to 15 seconds to accommodate network latency, allowing real URLs to resolve successfully [1].

D. Tilde Console Toggle & Packet Deduplication
- Integrated standard backtick/tilde (`~` / `KEY_QUOTELEFT` / `KEY_ASCIITILDE`) physical key event listeners directly inside `player.gd` [1]. Toggling console focus now calls `get_viewport().set_input_as_handled()` to prevent characters from bleeding into typing fields [1].
- Implemented a time-based packet deduplicator in `sync_node.gd` that discards identical packet payloads received within a 200ms window, resolving double-printing over full-mesh connections [1].

3. LOCAL TESTING MODE CONFIGURATION
-------------------------------------------------------------------
Local development operates across a coordinated port exchange:

- WINDOW 1 (Player 1): Listens on 8080 <-- Sends targets to 8081 [1]
- WINDOW 2 (Player 2): Listens on 8081 <-- Sends targets to 8080 [1]

The dynamic port-probing system sets up this loopback channel automatically upon launching two game windows on a single machine [1].

-------------------------------------------------------------------
4. COMPLETED CLOUDFLARE ONLINE TUNNELING INTEGRATION
-------------------------------------------------------------------
Cloudflare quick tunnels have been fully integrated to route raw gaming payloads over the public internet using standard web protocols [1]:

1. Expose Host: Player 1 hosts the game and initiates the Cloudflare quick tunnel (`chat -s`), exposing local port 8080 via the secure Cloudflare edge [1].
2. Dynamic WSS Routing: Player 2 inputs the generated trycloudflare subdomain (`chat -j <token>`) [1]. The client establishes a secure WebSocket (`wss://`) handshake over port 443 [1]. Cloudflare handles the HTTP Upgrade headers and proxies the WebSocket connection to the local listener [1].
3. Clipboard Integration: The host's extracted TryCloudflare URL is automatically copied to the system clipboard upon successful tunnel establishment, allowing rapid sharing [1].
4. Client Simplicity: No third-party tunneling software, access keys, or client-side setups are required on Player 2's computer [1].
